## 2. Согласованные маршруты 1С — сервер-потребитель Mapper

1С реализовала HTTP-сервис по адресу `http://192.168.10.30/erp_update/hs/catalog` (доступность из контейнера пока проверить на целевом хосте). Это **адрес источника для исходящих запросов Mapper**, а не адрес webhook.

- `GET /export`: **полная** выгрузка JSON (около 23 МБ, ориентировочно 10 с), включая помеченные на удаление позиции, без групп. Формат тела: `{"items":[{...}]}`. Используется для bootstrap и ежедневной сверки, не заменяет PostgreSQL.
- `GET /items?q=клапан&limit=20`: поиск по коду/наименованию/артикулу, только активные, `limit` от 1 до 50. Маршрут остаётся необязательным диагностическим/резервным: штатный поиск Mapper должен работать по собственной PostgreSQL, без N+1 запросов в 1С.
- `POST /items/batch`: `Content-Type: application/json`, тело `{"guids":["UUID1","UUID2"]}`, ответ `{"items":[{...}]}`, включает и помеченные на удаление. Использовать для webhook-upsert. Размер пачки — конфигурируемый, первоначально не более 50 GUID за запрос до согласования реального лимита 1С.

**Обязательные поля каждой карточки в ответах `/export` и `/items/batch`:**

```json
{
  "guid": "3c660a4a-ed29-11e6-8281-305a3a813380",
  "code": "00000052163",
  "name": "Манометр радиальный Д100",
  "full_name": "Манометр радиальный Д100 ТМ-510Р.00 (0-1,0МПа) G1/2.1,5 РОСМА",
  "unit": "шт",
  "article": "00000006836",
  "brand": "",
  "manufacturer": "РОСМА",
  "deleted": false
}
```

Все текстовые поля строго строковые, `deleted` — boolean, `guid` — UUID настоящей ссылки на `Справочник.Номенклатура`; `code` всегда строка с ведущими нулями. Пустые `article`/`brand`/`manufacturer` допустимы. Проверять валидность UUID, типы, длины, дубли GUID, дубли/конфликты кодов, аномально малое число строк и полноту. `full_name` использовать как предпочтительное поисковое наименование (как `НаименованиеПолное` в действующем XML); исходный `name` также сохранить в метаданных без потерь. Не добавлять несуществующие поля `price`, `group` и т. п.

Удалённые (`deleted=true`) исключаются из активного поиска и Qdrant; для полной выгрузки физически удалённые определяются отсутствием GUID относительно предыдущего полного снимка. В webhook отсутствие карточки в `/items/batch` **само по себе не считается доказательством физического удаления** без явного события `delete`.

### 2.1. HTTP полнота и безопасность

Согласовать с программистом 1С **небольшое дополнение**: успешный полный ответ `GET /export` должен отдавать `HTTP 200`, `Content-Type: application/json; charset=utf-8`, заголовок завершённости `X-Catalog-Complete: true`; желательно `Content-Length` и `ETag`/версию выгрузки. Это контракт, **ещё не подтверждённый Антоном**; не изображать заголовок существующим. Если 1С пока его не отдаёт, включение production синхронизации блокировать до согласования эквивалентного проверяемого признака, а не молча считать любой JSON полным.

Полная выгрузка — согласованный консистентный срез, не случайная порция записей. Никакой пагинации в этой версии. Не принимать `{items:[]}`, усечённые/некорректные ответы, дубли GUID, неполные JSON и критический внезапный обвал количества без явного подтверждения оператора. Предусмотреть configurable guard существенного сокращения активного каталога (например, более 10% за один sync) с сообщением и сохранением прежней рабочей версии. Нормальная массовая очистка должна иметь отдельную явную подтверждённую процедуру, не скрытый fallback.

1С сейчас сообщила `Basic Auth`, временно логин сотрудника и пустой пароль, а адрес **HTTP**, не HTTPS. Это неприемлемая конфигурация для production. Не помещать логин/пароль в URL, JS, Git, логи или API-ответ. Запросить отдельную **read-only сервисную учётную запись с паролем** и HTTPS (или защищённый транспорт VPN/TLS reverse proxy) и сетевое разрешение от контейнера Mapper до `192.168.10.30`. Тестовый HTTP разрешать только через явный server-side opt-in в изолированной среде с allowlist точных host/IP/port; не понижать безопасные значения по умолчанию и не делать обход контроля SSRF/redirect/DNS pinning. Ни одного `Basic` секрета по незащищённой сети без отдельного явно утверждённого исключения владельца.

Текущий `src/infrastructure/catalog_sources.py` запрещает JSON (`expected_format=xml`), использует `Accept: application/xml` и XML parser. Адаптировать, не переписывать: сохранить `source_type=http_onec`, разрешить `expected_format=xml|json`, `export_mode=full`, `GET`; разделить парсеры за существующим `CatalogSource` портом, возвращающие `ParsedCatalog`. Старый `local_xml` и старый `http_onec/xml` должны продолжить работать. Сделать потоковое скачивание, ограничение размера, `Content-Type` и completion header по формату, запрет redirect/SSRF, временный spool при больших ответах, защита от JSON bomb/неразумной глубины и ограничение числа строк. Не путать 23 МБ каталога и существующий `MAX_RESULT_BYTES` документов сопоставления.

## 3. Webhook — новый входящий API Mapper

**Точный адрес для Антона:** `POST http://192.168.55.3:8087/api/v1/catalog/events` (LAN/VPN; production предпочтительно HTTPS reverse proxy). Эндпоинта **нет** в текущем `ec26642`, его необходимо реализовать.

### 3.1. HTTP-контракт события V1

```http
POST /api/v1/catalog/events
Content-Type: application/json
X-Webhook-Key: <отдельный секрет webhook 1С>
```

```json
{
  "event_id": "5a12d947-30d3-4fd9-949a-9da4d765913a",
  "occurred_at": "2026-11-11T13:00:00Z",
  "changes": [
    {"guid": "3c660a4a-ed29-11e6-8281-305a3a813380", "action": "upsert"},
    {"guid": "8f157ccb-ed29-11e6-8281-305a3a813380", "action": "delete"}
  ]
}
```

`event_id` — уникальный и стабильный идентификатор отправки, при повторе должен сохраняться; `occurred_at` — UTC ISO 8601; `changes` — непустой массив из 1–100 элементов; `guid` — настоящий UUID 1С; `action` — `upsert` (создана/изменена/помечена на удаление) или `delete` (физически удалена и больше не возвращается из `/items/batch`). Приложение допускает опциональный монотонный номер/версию события, если 1С её предоставит, для подавления устаревших событий. Никаких обязательных новых REST-маршрутов в 1С, кроме трёх уже сделанных.

**Что должна делать 1С:** асинхронно формировать event из регистрации изменений/очереди обмена, не делать медленный HTTP-вызов внутри транзакции записи справочника; при недоступности Mapper повторять тот же `event_id` с backoff до успешного `202/200`. Для пометки удаления отправлять `upsert` — Mapper запросит карточку и увидит `deleted:true`. Для физического удаления **до удаления** сохранить GUID в outbox и отправить `delete` даже если карточку больше нельзя прочитать. Разрешить батч событий. Источник событий должен иметь устойчивую доставку; ежедневная полная сверка остаётся страховкой потерянных событий.

Ответ на новый event: `202 Accepted` с `event_id` и `status=queued`, **только после durable commit в PostgreSQL + outbox**. Повтор того же `event_id`/payload: `200` или `202` с прежним статусом, без второго задания; тот же id с другим payload: `409`. Недопустимый формат: `422`, неверный секрет: `401/403`, временная перегрузка: `429/503` с retry, излишне большое тело: `413`. Не заставлять 1С ждать embeddings или Qdrant в HTTP-ответе.

### 3.2. Безопасность webhook

Добавить выделенный server-only секрет `ONEC_CATALOG_WEBHOOK_KEY`, генерируемый bootstrap без перезаписи существующего `.env`; отдельный header `X-Webhook-Key`. **Не** принимать `API_KEYS[onec]` как административное право и **не** использовать `CATALOG_ADMIN_KEY` или операторский ticket. Сравнение секретов в постоянное время, отдельный rate limit и IP allowlist, bounded body, без PII/secret в логах. Желательно HTTPS или закрытый VPN/сегмент; не публиковать endpoint в интернет. Нельзя позволять payload менять URL, credentials, внешний источник, произвольные SQL/Qdrant коллекции или запускать shell.

### 3.3. Работа worker по событиям

1. Подтверждённые events сохраняются в новой собственной PostgreSQL-таблице с уникальным `(source, event_id)`, статусом, попытками и ошибкой. Отправка в RabbitMQ — **через существующий durable outbox**, lease/fencing, retry. Не использовать фоновые fire-and-forget задачи без durable commit.
2. Webhook-изменения объединяются в короткое окно, например 15–30 секунд, по GUID; повторные события и перекрытия coalesce. Не клонировать коллекцию из 62 тыс. точек **на каждое событие**; один stage на объединённую пачку.
3. `upsert`: запрашивать **текущую** карточку через `POST /items/batch` с ограниченными пачками. Если `deleted=false`, выполнить upsert/изменение; если `deleted=true`, исключить из активного каталога. Если карточка отсутствует и нет явного `delete`, сделать bounded retry, затем зафиксировать ошибку для полной сверки; **не удалять на догадке**.
4. `delete`: удалить GUID из активной версии и векторного индекса (после безопасной публикации), сохранить tombstone/аудит. Повторная доставка не создаёт ошибку. Устаревший webhook не должен перезаписать более новую карточку; при возможности опираться на версию 1С, иначе коалесцировать и перед публикацией перечитывать актуальное состояние через batch. Полная сверка — финальный источник истины.
5. Применять обновления через общий каталогический lock/staging/alias pipeline; действующая версия остаётся пригодной до завершения новой. Подтверждать applied events только после успешной публикации согласованного PostgreSQL snapshot и Qdrant alias. При сбое сохранять прежний индекс, доставлять retry без двойного применения.
6. При одновременной ежедневной полной выгрузке webhook не запускает конкурирующий индексатор; events аккумулируются и переигрываются/сверяются после commit полного снимка. При отсутствии начального полного каталога webhook сохраняется и обрабатывается после bootstrap или вызывает безопасную постановку полного импорта (без дублирования).
7. Не проводить векторизацию при изменении только non-semantic полей. Для изменения наименования/артикула/марки/производителя вектор обновляется, а не весь справочник. Для массового webhook burst установить лимиты, контроль очереди и fallback к очередной полной сверке.

**Нужно заложить в миграцию:** event log/outbox state, уникальные event ID, диагностический статус и данные для дедупликации. Миграции только additive (после существующей `0003_catalog_sync_dashboard.py`), не затрагивать snapshots approved документов.

## 4. Первоначальная миграция с UUID по коду на реальные GUID 1С

Это обязательный отдельный блок внутри **того же этапа** разработки, а не другая задача.

Сейчас XML парсер выбирает `CatalogItem.guid = uuid5(...code...)`, если GUID 1С отсутствует; при новом JSON он получает реальный `guid`. **Наивный переход сменит все идентификаторы и спровоцирует массовый reembedding**, потому что текущий `content_hash = digest(item.to_dict())` включает GUID/прочие метаданные.

Реализовать безопасное сопоставление старых и новых данных по однозначному коду, проверив уникальность и прежние конфликты. При наличии настоящего GUID хранить его отдельно как `onec_guid` и обеспечить стабильный внутренний ID со явно задокументированной политикой; не подменять ссылку 1С внутренним UUID. Предпочтительно сохранять текущий внутренний UUID при безопасно совпавшем коде и дополнять его `onec_guid`, а для новых записей выбирать стабильную детерминированную политику; обязательно хранить индекс `(onec_guid → internal_guid)` с уникальностью и поддержкой смены кода. Если политика требует перевода point ID на реальные GUID, делать это контролируемо в staging, не меняя старые immutable snapshots.

Отделить **semantic embedding fingerprint** (нормализованные данные, реально подаваемые на embedding, плюс model/preprocessing identity) от `metadata/content_hash`. Изменение GUID, кода, пометки удаления или иных несемантических полей не вызывает новую VLM/embedding генерацию; изменение `name/full_name/article/brand/manufacturer` — вызывает, если меняется реальный embedding input. Сохранить возможность переиспользовать уже вычисленные векторы и совместимость Qdrant alias, закрытых ссылок живых mapping jobs и rollback. Миграцию оценить счётчиками: added/changed/deleted/metadata-only/embedded/reused, не обещать ноль изменений point IDs.

Конфликтующие коды сохраняют действующую политику `quarantine` (не выбирать неоднозначную номенклатуру). Повторный настоящий GUID у разных карточек — ошибка всей выгрузки. Проверить, что смена кода одной реальной позиции не превращается в физическое удаление + создание независимого товара.

## 5. Новый контракт JSON спецификации — полная совместимость с Extracting

Фактический `spec-extracting-ai/main` на 11.11.2026 принимает/выдаёт:

```json
{
  "file_name": "spec_267-РД-ИТП.УУТЭ.pdf",
  "items": [{
    "Caption": "Манометр радиальный Д100 ТМ-510Р.00",
    "Units": "шт.",
    "Quantity": "2",
    "UserComment1": "267-РД-ИТП.УУТЭ",
    "Pages": "1",
    "Brand": "РОСМА",
    "Article": "00000006836",
    "Note": "подающий и обратный трубопроводы"
  }]
}
```

Это JSON **спецификации**, не путать с 1С JSON `GET /export` с полями `guid/code/name/...`.

Упомянутые восемь полей **все строковые**, в том числе `Quantity` (может быть `0,5`) и `Pages`; менять регистр/пробелы, схлопывать дубли, менять порядок и преобразовывать в числа запрещено. `file_name` — исходное имя PDF на верхнем уровне. Пустые `Brand`, `Article`, `Note` допустимы и должны присутствовать в новом ответе. `Brand` — бренд/производитель исходной спецификации; `Article` — артикул или код оборудования; `Note` — примечание позиции. Не заменять эти поля данными найденной позиции 1С.

### 5.1. Обновление входов и обратная совместимость

- `POST /api/v1/mappings/import-json`: принимать новый объект с `file_name` + всеми 8 полями в `items`.
- `POST /api/v1/mappings` с `source_job_id`: серверный polling `spec-extracting-ai` теперь получает тот же новый объект. `HttpExtractionSource.fetch` должен принимать его без `invalid_source`.
- Старые **пятиполейные** JSON без `file_name` и `Brand/Article/Note` должны оставаться валидными: отсутствие новых полей трактуется как пустые значения только в производном представлении; **не переписывать уже сохранённые исторические оригиналы/approved snapshots**. Для нового формата все перечисленные ключи обязаны сохраняться. Не принимать ошибочные типы, гигантские поля и неподтверждённые произвольные дополнительные реквизиты; зафиксировать версионированные схемы и контрактные тесты.
- Сохранять raw-source полностью (включая `file_name`) и отдельно производную нормализованную модель для поиска. Вся существующая проверка owner/idempotency/TTL/sha/revision должна остаться; hash включает всю исходную информацию, не только пять старых полей.

### 5.2. Результаты — **все поля без потерь**

После выполнения задания следующие API должны возвращать новые исходные данные целиком:

1. `GET /api/v1/mappings/{job_id}/source.json`: полный входной JSON с оригинальными `file_name`, восемью полями и тем же порядком `items`. Для legacy jobs без `file_name` сохранять совместимое старое поведение либо отдавать `file_name=""` по документированному правилу — без изменения сохранённой записи.
2. `GET /api/v1/mappings/{job_id}/result`: `items[].source` содержит все **восемь** полей, `file_name` доступен на уровне результата как metadata. Строка UI показывает `Brand`, `Article`, `Note`, имя PDF в заголовке; длинные примечания допускается раскрывать без изменения текста; никакой HTML-инъекции через названия/примечания.
3. `GET /api/v1/mappings/{job_id}/result.json`: добавить top-level `file_name`; в `items[]` сохранить восемь оригинальных полей **плюс** уже существующие `index`, `onec`, `matching` и метаданные. Не смешивать `Brand` источника с `onec.brand`.
4. `GET /api/v1/mappings/{job_id}/approved.json`: те же `file_name` и восемь полей на каждой строке, а также прежние `approved_at`, `approved_revision`, `approval`, `onec`, `matching`; неизменяемость и атомарное массовое утверждение сохраняются. Отказ по строке по-прежнему `onec:null` и confirmed=true после approval.
5. `GET /api/v1/mappings/{job_id}/result.xlsx`: колонки для `file_name`, `Brand`, `Article`, `Note` рядом с прежними исходными полями и отдельными полями выбора 1С. Строки `Quantity`, `Article`, `code` и формулоподобные строки — безопасный буквальный текст. Не терять ведущие нули и дубли.
6. Web import готового JSON, экран сопоставления, поиск/фильтры и боковая панель должны читать новые поля и показывать их без деградации старых заданий.

Пример целевого `approved.json` (демонстрационный, ссылки UUID не реальные):

```json
{
  "job_id": "11111111-1111-4111-8111-111111111111",
  "file_name": "spec_267-РД-ИТП.УУТЭ.pdf",
  "status": "approved",
  "approved_revision": 2,
  "approval": {"owner": "api:onec", "approved_revision": 2, "catalog_version": "...", "approved_at": 0},
  "items": [{
    "Caption": "Манометр радиальный Д100 ТМ-510Р.00",
    "Units": "шт.", "Quantity": "2", "UserComment1": "267-РД-ИТП.УУТЭ", "Pages": "1",

    "index": 0,

```

Пример схематический: в настоящем ответе сохранить **все уже существующие** поля и даты, не заменить их примером и не изменять их типы.

### 5.3. Использование новых полей в подборе

Семантический поиск/правила могут использовать `Brand` и `Article` **как отдельные достоверные признаки**, не выдирая их повторно из `Caption`: бренд сопоставлять с `brand`/`manufacturer`, артикул — с `article`/достоверно идентифицированным кодом; несовпадение точного артикула/производителя не должно автоматически утверждаться даже при высоком cosine. `Note` сохранять неизменно и использовать для техпараметров только при явно доказуемой релевантности; фразы «уточнить при монтаже» не считать моделью, маркировкой или обязательным техническим параметром. `file_name` не включать в embeddings. Не менять пороги без регрессионных тестов; при изменении правил обновить `ALGORITHM_VERSION` и проверить качество на корпусе, включая реальные строки из предоставленного JSON. В первую очередь требование **lossless pass-through**, улучшение качества не должно ломать это требование.

## 6. Сохранение scheduler, ручного обновления и UI

- `15:00 UTC` и включение/выключение через PostgreSQL оставить. Плановый sync — полный `GET /export` JSON для восстановления пропущенных вебхуков. Если в будущем потребуется изменить период, делать через текущую operator form, не hardcode в worker.
- Кнопка «Обновить сейчас» для всех обычных web owners после подтверждённого HTTP-источника остаётся с глобальным SQL cooldown 60 секунд, unchanged `POST /api/v1/catalog/refresh` и idempotency. Она запускает полный JSON-sync; не исполняет webhook-patch и не принимает URL/credentials в запросе.
- Webhook event endpoint — отдельный узкий API, **не наследует минутный cooldown кнопки**, но имеет свой auth/rate limit/dedup/concurrency.
- UI: опция формата `JSON/XML` при источнике `HTTP API 1С`, JSON по умолчанию только после выбора/конфигурации нового источника; existing XML настройки совместимы. Видимый URL источника — из PostgreSQL, секреты только server-side. Кнопки `Проверить подключение`, `Сохранить`, `Обновить сейчас`, история run и статусы должны работать; probe проверяет настоящий JSON, полноту и auth, но не публикует индекс.
- Добавить оператору аккуратный блок «События 1С»: статус webhook, количество принятых/ожидающих/применённых/ошибочных событий, время последнего успешного применения, ссылку на безопасный технический журнал; не раскрывать HTTP headers с ключами и полные карточки товаров. Webhook API URL отображать как read-only для копирования; webhook key **никогда** не раскрывать в UI. Обычные пользователи видят только безопасный агрегированный статус.
- Существующие `/mapping`, `/jobs`, `/catalog`, `/operator`, API docs, Top-5, выбор/`null`, крестик, общая кнопка утверждения и `approved.json` не терять.

## 9. Критерии приёмки и тесты

Обязательные тесты с чётким различием mock/real:

**Каталог:**
- Полный JSON 1С, корректный `deleted`; 65k карточек/23MB, streaming, timeout, ограничение тела;

- полный sync в 15:00 UTC, probe, manual refresh 60s, rollback/staging/Qdrant alias, restart/resume, unchanged secrets.

**Webhook:**
- 202 после durable commit и без ожидания Qdrant; duplicate replay same event id, hash-conflict 409, invalid secret 401, 100+ элементов 422, flooded 429;
- upsert нового, изменение бренда/артикула, пометка `deleted=true`, физический delete, repeated delete, missing batch result без delete, неупорядоченные события и повтор при ошибке 1С;
- параллельный full sync и webhook, worker crash между outbox и RabbitMQ, retry/lease/fencing, no duplicate application; 2 воркера не повреждают alias;
- событие не публикует частичный PG/Qdrant снимок, прежний каталог остаётся доступным при ошибке; после восстановления событие доходит; массовый webhook burst coalesces и не создаёт отдельное клонирование индекса на каждый GUID.

**JSON спецификации:**
- Дословный полный пользовательский пример с `file_name`, 8 полями, пустыми `Brand`/`Article`/`Note`, кириллицей, `Quantity="0,5"`, одинаковыми повторяющимися строками и формулоподобными значениями;

- roundtrip через PostgreSQL: `source.json`, `result` (включая `source`), `result.json`, `result.xlsx`, `approved.json` сохраняют все поля, Unicode/дубли/порядок и `file_name`;

- вариант без соответствия — `onec:null`, человек подтверждает все строки одной операцией, immutable snapshot не меняется при поздней sync;
- качество: Brand/Article конфликт проверяется, Note не вызывает ложных совпадений, `file_name` не влияет на embeddings;
- owner isolation, CSRF, header API keys, TTL 1 час документов не меняются.

**Гейты и отчёт:** Windows PowerShell `ops/check-quality.ps1`, Ruff + format + `pytest` (offline, API, architecture), Node, Chromium E2E, `git diff --check`; изолированные Linux integration tests с реальными PostgreSQL/Qdrant/RabbitMQ и shared embedding; отдельный smoke с **реальным** API 1С после настройки сетевого доступа/сервисной учётной записи, не выдавать fake за real. ## 10. Definition of Done

1. 1С `GET /export` отдаёт полный проверяемый JSON, который Mapper может загрузить через GUI и существующий планировщик в PostgreSQL/Qdrant; предыдущий рабочий каталог сохраняется на любой ошибке.
2. `POST /api/v1/catalog/events` защищён выделенным ключом, принимает события от 1С, быстро и идемпотентно фиксирует их; worker через `POST /items/batch` изменяет **только необходимые** позиции, удаляет помеченные/физически удалённые, сохраняет согласованность со staging/alias.
3. Ежедневный полный sync остаётся гарантированной сверкой и устраняет пропущенные webhook события; ручной refresh и операторские права не сломаны.
4. Фактический JSON Extracting с 8 полями + `file_name` проходит оба входа Mapper, UI, source/result/approved JSON, Excel без потери значений; legacy 5-полейный JSON не ломается.
5. Старые интеграционные пути/ключи, Top-5, ручное подтверждение, approve, постоянный каталог, TTL, безопасность, health и production volumes сохранены.
6. Обновить OpenAPI, интеграционную инструкцию 1С (включая outbound webhook, секрет, обработку HTTP статусов), архдокументацию, примеры и тесты. В конце предоставить gap analysis, точный список файлов, результаты тестов, предупреждения, Windows PowerShell команды и безопасный Linux rollout/rollback. Сформировать явный `git add <paths>` и команды commit/push для **ручного** исполнения владельцем; самостоятельно не выполнять.
