## 2. Подтверждённые дефекты и наблюдения

### 2.1. Дубли пользовательских заданий

`src/web/static/js/invoices.js`: `uploadButton.disabled=busy; files.disabled=busy; jsonInput.disabled=busy;`. `busy` сбрасывается сразу после POST/open, пока job в очереди либо обрабатывается. После успешного POST генерируется `pendingUploadKey=newIdempotencyKey()`. Повторный клик с теми же файлами получает новый idempotency key и создаёт новый job, вместо восстановления предыдущего. Импорт JSON имеет похожий риск повторной операции. Серверная идемпотентность по owner/key не запрещает разные ключи.

### 2.2. Потеря активного задания в UI

`src/web/static/js/app.js` открывает job только при наличии `?job=<UUID>`. Переход по ссылке `/invoices` или `/mapping` без query показывает пустое состояние, хотя обработка продолжается. В `base.html` страница `/mapping` визуально относится к пункту «Задания»; в `jobs.js` ссылки открытия/экспорта строятся только для `/mapping` и `/api/v1/mappings`. Legacy list `/api/v1/mappings` исключает invoice. Нужно проверить фактическую выдачу dashboard job kind и разделить маршрутизацию по профилям.

### 2.3. Отсутствие полноценного прогресса и отмены

`invoices.js` опрашивает status примерно раз в секунду, показывая `В очереди · 0/0`. В `src/infrastructure/http_clients.py`, `fetch_profile()` считывает статус 8083, но передаёт в progress практически только polling/fetching, теряя per-file/page/этапы и время. `src/infrastructure/invoices/extracting.py` сохраняет конечное предупреждение, но не полный безопасный progress snapshot. В Mapper нет управляемой отмены для этой цепочки. Отсутствие browser events не означает остановку worker.

### 2.4. Накопление сообщений — отдельный backend-дефект

`src/infrastructure/repositories.py`, `SqlJobs.pending()`: для nonterminal jobs без действующего lease выбирает также `dispatched_at < now - 30`. `src/worker.py`, `maintenance()`: каждые 3 секунды публикует их и вызывает `dispatched()`. Поэтому подтверждённо опубликованные queued jobs, ожидающие освобождения worker, могут повторно попадать в RabbitMQ через 30 секунд. Защита claim/lease предотвращает одновременное выполнение, но не накопление копий. По умолчанию `worker_concurrency=2`, и на скриншотах было 2 Unacked; реальное значение проверить из runtime, не увеличивать его как workaround.

| Наблюдение `spec_mapper.jobs` | Ready | Unacked | Всего |
|---|---:|---:|---:|
| Первый скриншот | 9 | 2 | 11 |
| Второй скриншот | 56 | 2 | 58 |
| Последний `rabbitmqctl` | 70 | 2 | 72 |

В последнем выводе 1 consumer. У 8083 тогда было 10 Ready, 1 Unacked, 1 consumer. Это количество сообщений, а не уникальных jobs; без сверки БД и диагностических метрик невозможно установить точное число дублей. Stage 03A устраняет аналогичный дефект в 8083, но не устраняет независимую проблему Mapper.

## 3. Защита от повторного создания

### 3.1. Frontend

Ввести явное состояние логической операции (не путать с кратким `busy` запроса): `idle`, `submitting`, `queued`, `extracting`, `matching`, `cancelling`, `awaiting_review`, `approved`, `cancelled`, `failed`, `expired` и состояние временной потери соединения. Реальные статусы API нормализуются только на UI; неизвестное состояние — явная диагностика, не успех.

- Нажатие «Извлечь и сопоставить» сразу, до первого await, блокирует повторный submit, выбор файлов/страниц и альтернативный JSON-вход для текущей операции. Показывает визуальную реакцию (spinner + «Отправка файлов…»). После 202 кнопка остаётся недоступной, меняет текст на «В очереди…»/«Извлечение…»/«Сопоставление…». Не отображать активную форму под видом возможности повторить уже начатое действие.
- Один логический запуск — один стабильный `Idempotency-Key`. При сетевой ошибке после POST не считать, что сервер ничего не принял; восстановить UUID/повторить тот же запрос с тем же ключом. Не генерировать ключ автоматически при успешном ответе. Новый ключ — только новое явно начатое задание или сознательно изменённый payload перед отправкой; сохранить прежний при неопределённом результате. Не хранить оригиналы, секреты, денежные JSON в localStorage. При F5/закрытии вкладки восстанавливать с серверной истории; при необходимости повторно выбрать файл для неопределённой отправки и сверить идентичность.
- Применить одинаковые правила к импорту готового JSON, запуску спецификаций и legacy UI там, где инициируется новое задание. Оставить возможность осознанно создать другой пакет через отдельную команду «Новое задание», а не через повторный клик текущей формы. При новом запуске сохранить доступ к уже обрабатываемому/неутверждённому заданию; не требовать закончить все предыдущие jobs для независимого пакета.
- Показать понятный результат 409/429/413/422, Retry-After, ошибку сети. Не оставлять бесконечный spinner и не уничтожать текущий выбор/прогресс при transient failure. Отмена HTTP-запроса браузера не равна отмене принятого job.

### 3.2. Backend

Сохранить существующий контракт `Idempotency-Key`: одинаковый owner/key/payload возвращает прежний job; другой payload под тем же ключом — 409. Добавить атомарное предотвращение одинаковых **активных** заданий в рамках owner и соответствующего профиля (specification/invoice; legacy — совместимая защита в пределах того же вида входа). Использовать канонический fingerprint: упорядоченные SHA-256 файлов, выбранные физические страницы, значимые параметры (например, project_code), профиль и вид входа; для JSON — полный canonical source, для ссылки на job 8083 — source_job_id. Нормализовать только технически эквивалентные параметры; не склеивать разные документы/порядок/шифры и не считать JSON-вход равным произвольному PDF-входу. Не изменять исходный payload.

- Новые ключи для одинакового активного входа не должны создавать копию job/временных файлов/outbox. Возвращать существующий UUID с документированным признаком `reused` или эквивалентным обратно совместимым полем. Защитить параллельные POST/несколько вкладок/API replicas средствами БД (уникальность/транзакционный lock), не только проверкой перед INSERT. Привязка повторного ключа к ранее принятому job должна сохранить семантику idempotency conflict и после завершения.
- Не раскрывать совпадения между разными owner, не запрещать осознанный повтор после terminal/отказа/нового запуска. Активным считать технически обрабатываемый job; draft на review доступен и должен быть видимым, но правила осознанного повторного запуска после review документировать отдельно. Не менять старые обязательные поля и успешные HTTP-коды без согласования. Если найден реальный конфликт с legacy контрактом — обозначить `REQUIRES_OWNER_DECISION`, выбрать минимальный обратно совместимый вариант, а не молча менять интеграцию.
- Добавить bounded admission/backpressure: ограничения количества активных/queued jobs и общего размера временных данных в собственном сервисе, проверяемые атомарно; понятный 429/Retry-After или существующий согласованный код при перегрузке. Значения выбрать/обосновать из текущей конфигурации и нагрузки; не вводить жёсткие произвольные ограничения общему RabbitMQ. Не изменять действующие лимиты 1–10 файлов, 50 MiB/файл, 100 MiB/пакет, 100 страниц без отдельного решения.

## 4. Компактный пользовательский интерфейс

Сохранить действующий светлый инженерный стиль Mapper. Улучшить usability без нового дизайн-фреймворка, больших пустых панелей, повторяющихся заголовков и лишнего вертикального скролла. Учитывать desktop и узкие экраны. Ниже схема компоновки, а не требование переписать страницу целиком:

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ Сопоставление счетов   [Спецификации] [Счета]     Активные: 2   [+ Новое]  │
├────────────────────────────────────────────────────────────────────────────┤
│ Пакет из 3 файлов · 12 страниц                  Извлечение · 06:24       │
│ [Выбрать файлы]   [Готовый JSON]    [Извлечение…]    [Отменить]           │
│  ▸ Файлы и диапазоны (3)                      ▸ UUID / технические детали│
├────────────────────────────────────────────────────────────────────────────┤
│ ✓ Принято → ✓ Очередь → ● Извлечение → ○ Подбор → ○ Проверка → ○ Утвержд. │
│ Страницы 6/12  ██████████░░░░░░░░░░ 50%       Строки: определяются       │
│ ✓ ЭМИС… 3/3       ● Русский Свет… 3/5      ○ Русский Свет… 0/4           │
│ ▸ Журнал этапов (8)     Последнее: обработка страницы 6                   │
├────────────────────────────────────────────────────────────────────────────┤
│ Файлы 3 | Документы — | Позиции — | Подобрано — | Проверить — | Финансы —  │
│ ▸ Финансовые предупреждения                    [Утвердить] [Экспорт ▾]  │
│ Поиск / фильтры                                                          │
│ Таблица позиций и существующий dialog выбора                              │
└────────────────────────────────────────────────────────────────────────────┘
```

Значения в макете условны; UI показывает только фактические данные. Требования:

- Одна компактная панель загрузки, управление диапазонами страниц в компактном списке/раскрываемом блоке (не гигантский отступ на каждый файл). Названия не обрезать без возможности прочитать полностью. Счётчики — одна компактная полоса, с переносом при узком экране, а не шесть больших карточек. Журнал по умолчанию компактный (последние 3–5 событий или последнее событие + раскрытие полного списка). Финансовый блок компактный, но обязательные предупреждения и подтверждения нельзя скрыть так, чтобы их не заметили.
- Во время обработки на первом экране видны активный этап, реальный прогресс, последняя активность и отмена; таблица остаётся доступной после завершения. Не размещать кнопку отмены далеко внизу. На экране 1366×768 при обычном масштабе основные действия и ход обработки видны без вертикальной прокрутки в типичном сценарии 3 файлов. Для 10 файлов использовать раскрываемый список/scroll области; не скрывать ошибки в свернутой панели.
- По завершении выделить «Готово к проверке», показать реально извлечённые позиции, кандидатов, финансовые предупреждения и действие утверждения. Существующие таблица, поиск, выбор, null, preview и экспорт сохраняются. Отдельно показать ограничения, когда preview недоступен у импортированного JSON.
- Доступность: явные названия кнопок, aria-live для важных переходов без спама, aria-busy/disabled, фокус/клавиатура, подтверждение отмены, статус не только цветом. Не передавать confidential данные через HTML/JS-логи. Сохранить CSP, локальные ресурсы, security.

## 5. Навигация и восстановление заданий

Меню: «Главная», **«Сопоставление спецификаций»** (`/mapping`), **«Сопоставление счетов»** (`/invoices`), «Все задания» (`/jobs`), остальные существующие разделы. Исправить активный пункт, breadcrumbs, заголовки, ссылки и экспорт. Не переименовывать URL/старые API, только понятные UI labels; общий журнал не удалять. Ссылки «Спецификации»/«Счета» должны открывать соответствующее рабочее пространство, а не чужой профиль или пустой экран при наличии активных задач.

Серверный источник истины — PostgreSQL, не память браузера. Реализовать owner-safe list/filter по профилю (например `GET /api/v1/invoices`, `GET /api/v1/specifications` либо обратимо расширенный `/api/v1/dashboard/jobs` с `profile`/`kind`). Использовать общую пагинацию/сортировку и существующую БД. Не менять старый `/mappings` list так, чтобы он неожиданно возвращал invoice DTO. UI общего журнала обязан различать `invoice`, `specification`, legacy `mapping` и административные работы (каталог), строить корректный deep link и доступные экспорты. Проверить оба профиля, все списки и operator view. Чужие задания остаются только разрешёнными метаданными, без доступа к результату/отмене.

При входе в рабочее пространство:

1. Если есть валидный `?job=UUID`, открыть это своё задание правильного профиля. Чужое/истёкшее — честная диагностика и список своих доступных заданий, без утечки/тихого запуска другого job.
2. Если UUID нет, получить список собственных неистёкших задач. Восстановить последнее активное задание либо показать компактный список/переключатель, если их несколько. Включить также `awaiting_review` и доступные terminal результаты. Не переключать открытый job на более свежий самопроизвольно.
3. Если задач нет — форма нового задания. Список доступен при переключении профилей; одинаковое поведение после F5, navigation, закрытия/повторного открытия вкладки при действующей owner-сессии. После смены/истечения сессии не обещать доступ к чужим задачам.
4. Не прекращать backend job при уходе со страницы. Закрывать только frontend subscription, таймеры и устаревшие HTTP-запросы. Не создавать новый job при GET/refresh/reconnect. Отображать время до истечения TTL и понятный результат 404/410. Не продлевать TTL из-за просмотра.

## 6. Прогресс, журнал этапов и SSE

Новый Mapper — orchestrator для 1С и UI, а не второй extractor. Получать безопасный фактический progress из API 8083. `fetch_profile()` уже выполняет polling; расширить существующий transport/callback (либо использовать один upstream SSE-поток с fallback, если это обоснованно фактическим контрактом) так, чтобы `JobProcessor` сохранял progress durable. Не создавать отдельный цикл polling/SSE upstream на каждую браузерную вкладку. Не отправлять повторный запрос VLM ради прогресса.

### 6.1. Нормализованный snapshot и события

Предусмотреть общую модель lifecycle в Mapper с profile-specific адаптерами. Поля (названия могут следовать существующему стилю, но документируются): внешний `job_id`, profile, status, stage, revision, создано/начато/обновлено, expires_at, elapsed/wait (из timestamps), progress по файлам/страницам, текущая стадия, текущий файл/физическая страница, total/processed позиций после извлечения, warning/error, `last_event_id`. Не выдавать внутренний upstream ID, URL, credentials, lease или raw VLM stream. Для legacy `source_job_id` входа также показывать доступный прогресс 8083; для готового JSON стадия extracting помечена как неприменимая, а не фиктивно пройдена VLM.

Отдельно отображать ожидание worker Mapper и очередь 8083 (если upstream сообщает queued), передачу файлов, извлечение/согласование/финансовую проверку по доступным данным 8083, получение финального JSON, matching batches, готовность к review, approval, error/cancel. Не придумать queue position, ETA, heartbeat от модели, проценты несуществующей стадии. До известного числа строк — «Определяется количество позиций» вместо `0/0`. Использовать фактические `processed_pages/total_pages`, `current_file_index/current_pdf_page`, `files[]`, и для matching — число durable сохранённых строк, включая явно отдельно обозначенные non-applicable. При неопределённой длительности — indeterminate indicator. Финансовая проверка выполняется 8083; Mapper показывает источник/предупреждения, не пересчитывает.

Сохранять в своей PostgreSQL bounded metadata snapshot и журнал значимых переходов с монотонным ID; события и изменение статуса атомарны. Не писать каждую одинаковую polling выдачу/токен и не хранить полный JSON в каждом событии. Upstream события при проксировании нормализовать в разрешённый safe набор, не дублировать при restart/reconnect. ## 7. Отмена: сквозной durable lifecycle

В обоих профилях и legacy добавить идемпотентную отмену с состояниями `cancelling`/`cancelled`, защитой owner/CSRF/API-key/TTL. Сохранить каталог/административные jobs вне этого механизма. В API status, list, Swagger, фильтрах, exports и UI отразить новые состояния. Не считать cancelled успешным/approvable. Не ослаблять существующие CAS/lease/fencing/approval.

| Состояние | Требуемое действие |
|---|---|
| `queued`, ещё не запущено upstream | Отменить атомарно, не вызвать 8083/VLM, не публиковать новые доставки |
| `extracting`, upstream создан Mapper | Durable отмена и запрос в соответствующий `POST 8083 .../{source_job_id}/cancel` серверным ключом. Подтверждение или ожидание terminal |
| `extracting`, legacy upstream создан внешним клиентом | Отменить только Mapper; не отменять независимое upstream-задание |
| `matching` | Остановить дальнейшие embedding/Qdrant batches и публикацию результатов |
| `awaiting_review` (внутренние complete/ready_for_review) | Разрешить явный отказ от неутверждённого результата; не менять каталог |
| `approved` | Запретить изменение утверждённого snapshot (409 или существующий согласованный код) |
| `cancelling`/`cancelled` | Повтор безопасен, возвращает актуальное состояние |

- Применить durable cancellation flag/transition, проверку перед внешними вызовами и после checkpoint, fencing старого исполнителя, атомарный конфликт cancel/approve/complete. Отмена `awaiting_review` — отдельный разрешённый переход; простого добавления `cancelled` в `TERMINAL` недостаточно. Ни одна доставка не должна возродить отменённый job. Обработать cleanup и отмену после restart.
- Не отменять задания 8083, созданные вне Mapper, или чужие jobs. Явно хранить принадлежность upstream-операции (managed vs external/import-json). Сохранить внутренний upstream ID, ключ идемпотентности и стадию передачи. Если cancel пришёл между отправкой POST и записью `source_job_id`, либо ответ потерян, использовать безопасное восстановление той же принятой операции по стабильному ключу/контракту 8083. Не создавать новый upstream job специально ради отмены, если неизвестно, был ли POST принят: обосновать восстановление по доступному контракту 8083 либо безопасное ожидание/диагностику. Не терять обязанность отменить уже принятый managed upstream после падения worker.
- Если 8083 временно недоступен, сохранить cancelling и ограниченный retry с backoff; не выдавать подтверждённую отмену upstream без доказательства. Если внешний VLM уже выполняется и не поддерживает немедленный abort, показать «Отмена запрошена, ожидается остановка текущей операции». При timeout/expiry явно диагностировать неопределённый исход. Не убивать shared-vlm или чужие процессы.
- В UI кнопка «Отменить» доступна при queued/extracting/matching, отдельное подтверждение отказа от draft, блокировка повторных действий на время запроса, продолжающийся progress до terminal. После terminal доступна команда нового задания. Файлы/результаты хранятся и очищаются по согласованному действующему TTL, без непредусмотренного продления.

## 8. Исправление доставки RabbitMQ в Mapper

См. дефект раздела 2.4. В рамках собственного репозитория повторить **принцип** принятого Stage 03A, но не копировать механически код другой БД/архитектуры. Изучить `src/infrastructure/repositories.py`, `src/infrastructure/database.py`, `src/infrastructure/broker.py`, `src/worker.py`, `src/application/processing.py`, `src/application/ports.py`, `src/domain/models.py`, `src/bootstrap.py`, настройки, catalog sync/events job kinds и тесты. Shared ничего не меняет.

- Durable состояние доставки отдельно от business lifecycle, атомарный job+outbox в PostgreSQL, conditional dispatcher claim, небольшие batches, confirm с conditional update, поколение доставки/ограниченный lease, transport attempts/backoff/jitter. Убрать перепубликацию подтверждённых jobs по `dispatched_at < now - 30` при обычном ожидании. Не просто увеличить 30 секунд и не отключить recovery. Не держать DB lock во время AMQP publish.
- Publisher confirm/NACK/unroutable/timeout/connection loss: корректная обработка, bounded retry и явная диагностика исчерпания/длительной недоступности. Проверить, что нераспределённые сообщения действительно не помечаются published (существующий `mandatory=True`, проверить on-return handling). Сохранить at-least-once; crash после confirm до DB commit может дать допустимый duplicate delivery, не обещать exactly-once. Stable message_id сам по себе не дедупликация RabbitMQ.
- Сохранить существующий claim/heartbeat/fencing и checkpoints; retry бизнес-операции создаёт ровно одну новую delivery attempt атомарно. При redelivery до истечения старого lease предусмотреть восстановление после смерти исполнителя без потери единственного сообщения и без горячего requeue. ACK только после durable checkpoint/terminal/retry или безопасного no-op. Отменённые/истёкшие/завершённые/неизвестные UUID не выполняются. Старые сообщения с UUID совместимы при миграции. При внешней утрате подтверждённой очереди — ограниченная явная reconciliation, не штатная перепубликация всех queued.
- Проверить весь общий dispatcher: `mapping`, `specification`, `invoice`, `catalog`, `catalog_events`. Административные jobs имеют собственные бюджеты, recovery и guards; не менять их контракты, каталог/вебхуки не должны потерять задания или получить повторные публикации. Защитить от starvation и бесконтрольного роста, не увеличивать worker_concurrency/prefetch как решение. Никаких глобальных broker policies/плагинов или новых shared queues. Если необходимо отдельное изменение аргументов своей очереди — сначала обосновать и согласовать; не ломать существующую декларацию.
- Проверить связь с 8083: сохранение upstream ID и стабильного ключа до следующего этапа, не запускать VLM повторно при restart/retry существующего Mapper job. Не считать сам факт transport retry поводом заново извлекать/сопоставлять уже durable подтверждённые данные. Сохранить каталог version/identity и исходные JSON без изменений.
- Метрики/логи: уникальные активные jobs по profile/state, publish attempts/confirms/errors, pending/recovery, duplicate delivery/no-op, lease recovery, ACK/retry, queue health, время ожидания, upstream progress и heartbeat. Не логировать raw financial payload, credentials, содержимое файлов. Никаких новых внешних observability сервисов. При отличии RabbitMQ counts и unique jobs объяснять, а не выдавать их за одно число.
