# Эксплуатация и приёмка

## Подготовка

Сервер должен иметь Docker/Compose 2.24+, `uv`, доступ к PyPI и image registry для
первой сборки. Shared стек предварительно запущен, существующая `ai-shared` содержит
RabbitMQ и `shared-embedding`. Скрипт ничего не устанавливает в systemd и не выбирает GPU.
RabbitMQ обнаруживается по Compose label service=rabbitmq и участию в ai-shared;
неоднозначное обнаружение останавливает запуск. Bootstrap читает существующие admin credentials RabbitMQ из Docker deployment в память
Pydantic, передаёт в Management API salted password_hash; пароль проекта не попадает
в argv/docker exec/журналы. Admin credentials в .env проекта не сохраняются.
Автоподготовка ограничена namespace
`spec_mapper`; существующий чужой пользователь/vhost или неверный пароль не перезаписываются.

Выберите XML из data/ либо подтверждённый HTTP источник и настройте открытые параметры.
В установленном сервисе источник переключается через операторский UI; bootstrap fallback
CATALOG_SOURCE_TYPE=local_xml сохраняется. В .env храните
реальные секреты и необходимые частные overrides. Upstream контейнер должен быть доступен по фактическому DNS:
значение EXTRACTING_BASE_URL в примере нужно сверить с вашим сервером.
Не требуется и не создаётся секрет shared-embedding.

При выборе локального XML файл игнорируется Git: `git pull` его не доставляет. Перед первым запуском
передайте файл с Windows (в отдельной PowerShell-сессии), заменив `ВАШ_ЛОГИН` своим:

```powershell
ssh ВАШ_ЛОГИН@192.168.55.3 "mkdir -p ~/projects/spec-mapper-ai/data"
scp ".\data\Номенклатура_вся.xml" ВАШ_ЛОГИН@192.168.55.3:~/projects/spec-mapper-ai/data/
```

```bash
bash scripts/up.sh
```

Обычный запуск не делает down, не удаляет volumes и не останавливает shared сервисы.
Первый импорт имеет отдельный deadline 24 часа (`CATALOG_IMPORT_TIMEOUT_SECONDS`)
и сохраняет offset пачек для продолжения staging после отказа. Часовой TTL mapping
не прерывает каталог. Worker журнал остаётся
видимым. Ошибка импорта останавливает up.sh даже при ранее существовавшем каталоге.
Старый индекс при этом остаётся доступным. Недоступные shared зависимости дают not ready.

V4: `up.sh` передаёт `import-catalog --configured-source --wait`, читает сохранённый
источник из SQL. HTTP bootstrap не требует XML; исправный постоянный каталог без
локального файла проверяется по модели/Qdrant count и сохраняется. Явный прежний
`import-catalog --wait` продолжает импортировать локальный XML.

Новая additive миграция 0004 не переписывает entries/jobs/approved snapshots.
Bootstrap атомарно добавляет ONEC_CATALOG_WEBHOOK_KEY, не меняя существующие секреты;
не выводит его в логи/GUI. Передайте ключ программисту 1С по защищённому каналу.

Полный HTTP JSON требует согласованного X-Catalog-Complete:true и allowlist.
12.11.2026 владелец проверил `/export`, `/items`, `/items/batch` с Ubuntu,
а GET `/items` — также из API-контейнера Mapper. Полная выгрузка:
65 493 карточки, 3 439 удалённых, 23 857 863 байта, 42,57 секунды, marker подтверждён.
Для этого API разрешён HTTP Basic с непустым username и пустым паролем при явном
ONEC_CATALOG_ALLOW_HTTP=true; host/IP/port проверки сохраняются. HTTP по умолчанию
запрещён, Bearer требует HTTPS, TLS verification не отключается.
После установки исправления задайте приватные overrides, включая timeout 120 и
CONTRACT_CONFIRMED=true, по [инструкции подключения](INTEGRATION_1C.md#подключение-подтверждённого-http-api).
CATALOG_SOURCE_TYPE=local_xml оставьте bootstrap fallback; сохранённый источник
в PostgreSQL меняет оператор в GUI. Сначала сохранить HTTP с расписанием OFF,
выполнить probe и ручную сверку, проверить журнал/количество, затем включить daily
15:00 UTC. Реальная обратная отправка webhook из 1С пока не проверена.

Защита сокращения: при catalog_shrink_guard проверьте источник и отсутствующие позиции.
Для заведомо правильного полного файла получите SHA-256 (`sha256sum export.json`),
задайте точный ONEC_CATALOG_SHRINK_ACK_SHA256 серверным override, перезапустите только
собственные API/worker и повторите импорт. После успеха очистите override; глобального
отключения guard нет. Обычные события delete не нуждаются в таком подтверждении.

## Обновление и проверки

После того как владелец проверил и отправил свои изменения:

Для подключения подтверждённого HTTP Basic API 1С сначала выполните отдельный
порядок из [INTEGRATION_1C](INTEGRATION_1C.md#подключение-подтверждённого-http-api):
выключите расписание и дождитесь активного импорта до пересоздания API/worker.
До первого ручного probe и импорта используйте `docker compose --env-file .env.example --env-file .env up -d --no-deps --build api worker`
вместо `bash scripts/up.sh`: общий bootstrap может импортировать уже сохранённый источник.
Ниже — обычное обновление после завершённой настройки источника.

Порядок `test.sh` → `up.sh` проверяет код до обновления работающих контейнеров.
Обычные тесты самодостаточны: поднимают временный HTTP-сервис и SQLite, используют
явные mock внешних зависимостей. Запуск production перед ними не требуется и
не устраняет сетевые сбои их отдельного loopback-сервера. `bash scripts/up.sh`
остаётся одной командой полного запуска; он не запускает Ruff/pytest, зато выполняет
bootstrap, миграции, импорт сохранённого каталога и ожидание readiness.
Проверки реальных зависимостей `test.sh --live` выполняются после `up.sh`.

```bash
git pull --ff-only origin main
bash scripts/test.sh
bash scripts/up.sh
bash scripts/test.sh --live
```

`test.sh` и `ops/check-quality.ps1` показывают логи. Linux требует Docker Engine,
`uv` и Node.js. Ruff/Node запускаются на хосте; Python/Chromium — в собственном
временном контейнере `--network none`, с loopback для тестового HTTP API.
При первой сборке тестовый образ скачивает Chromium и системные библиотеки;
слой зависимостей кэшируется независимо от исходников. Production runtime
браузер и dev-зависимости не получает. Устанавливать Chromium на Linux-хост не нужно.
Контейнер не монтирует `.env`, каталог, staging, Docker socket или volumes,
не публикует порты и не присоединяется к сетям проекта/shared. После проверки
`test-results/` и `.coverage` копируются в checkout, собственный контейнер удаляется.
Ошибка pytest сохраняет ненулевой exit code и останавливает последующие проверки.
На Windows Chromium устанавливает `ops/check-quality.ps1`.

В браузерных проверках импорта готовность определяется доступностью поля загрузки
после подготовки сессии и подключения обработчиков. Фоновая сводка «Каталог: …»
не является признаком готовности импорта; её задержка не блокирует форму.
При ошибке инициализации форма остаётся заблокированной, причина отображается в UI;
E2E дополнительно выводит HTTP-статусы/пути и ошибки JS без credentials.
V4-сценарий при падении сохраняет screenshot и Playwright trace в `test-results/`;
trace содержит только данные изолированного теста. Для просмотра:
`uv run playwright show-trace test-results/v4-normal-failure-trace.zip`.
Ошибка Chromium `net::ERR_NETWORK_CHANGED` при запуске непосредственно на Linux-хосте
прерывала загрузку JS-модулей до инициализации приложения. Поэтому offline HTTP API
и браузер выполняются в отдельном сетевом пространстве, а не с увеличенными timeout
или повторным выполнением упавшего теста.
В E2E общего утверждения GET-чтения через Playwright APIRequestContext допускают
два повтора только при ECONNRESET; HTTP 4xx/5xx и операции записи не повторяются.
Контролируемый TCP-сбой проверяет восстановление одного GET, отсутствие retry
на 503 и ошибку после трёх неуспешных попыток при постоянном разрыве.
Тест cooldown дожидается завершения конкретного refresh job: пустой outbox
`pending()` не означает, что worker уже закончил работу.
Бюджет E2E assertions — 15 секунд: UI обновляется раз в 10 секунд, retry status
после сетевого сбоя — через 5 секунд. API/unit timeout и настройки сервиса не меняются.
Падение такого E2E при `bash scripts/test.sh` останавливает проверку до обновления
рабочих контейнеров и само по себе не означает ошибку Basic 1С. Для подтверждённого API
задайте приватный override `ONEC_CATALOG_TIMEOUT_SECONDS=120` и сохраните timeout 120
в настройках уже установленного источника через UI; env не перезаписывает PostgreSQL.

`--live` запускает tests image в private+ai-shared без публикации DB/Qdrant портов.
Проверяет настоящий PostgreSQL, shared embedding, staging Qdrant/alias и RabbitMQ
publisher confirm/nack/redelivery. Использует отдельные smoke ресурсы и удаляет
только их. Не подменяет live проверки тестами с fake AI/broker.

Live-проверка контракта извлечения требует явного UUID готового API-задания:

```bash
docker compose --env-file .env.example --env-file .env run --build --rm --no-deps tests /app/.venv/bin/pytest -m live --source-job-id <UUID> -q
```

Без UUID upstream-тест помечается skipped. Тесты, меняющие глобальное расписание,
дополнительно требуют специального изолированного stack и пропускаются на production.
HTTP-цепочка onec → Top-5 →
поиск → выбор/null → approve → approved.json требует API_KEYS с onec и telegram
и готового каталога. Удаляются только собственные smoke-задания.

Для ручной повторной синхронизации, без пересчёта неизменившихся векторов:

```bash
docker compose --env-file .env.example --env-file .env exec -T api /app/.venv/bin/python -m src.cli import-catalog --wait
```

Daily sync выключен по умолчанию, время — 15:00 UTC. `CATALOG_DAILY_SYNC` и
`CATALOG_SYNC_TIME_UTC` читаются только при первом bootstrap SQL настроек. Затем
включение, время и источник сохраняет оператор в UI; перезапуск с другим env не
переписывает PostgreSQL конфигурацию. Подключение реальной 1С требует её контракта.

## Оператор и пользовательское обновление

`up.sh` поднимает собственный `operator-gateway` вместе с API/worker. Gateway
публикуется только на loopback сервера `127.0.0.1:8088` (`OPERATOR_PORT`), находится
только в отдельной сети operator_access с API, без ai-shared и Docker socket. Публичный web/API
сохраняет 8087, открывать 8088 в firewall/LAN не требуется. Порт должен быть свободен.

На Windows замените `ВАШ_ЛОГИН` своим SSH-логином:

```powershell
ssh -N -L 18087:127.0.0.1:8088 ВАШ_ЛОГИН@192.168.55.3
```

Откройте `http://localhost:18087/operator`, нажмите «Получить одноразовый код»,
введите показанный код и начните сессию. При подтверждённом gateway-входе SSH
инструкция скрыта. Выдача кода требует CSRF и подписанного 15-секундного gateway
proof, обычного Host=localhost недостаточно. Используется существующий SESSION_SECRET;
новых секретов или DB migrations нет. Код не записывается в browser storage.

Прежний туннель на серверный 8087 и HTTPS поддерживают резервный вход по CLI-коду:

```bash
docker compose --env-file .env.example --env-file .env exec -T api /app/.venv/bin/python -m src.cli operator-ticket
```

Изменение расписания/источника и его проверка остаются операторскими действиями.
Кнопка «Обновить сейчас» всегда использует `/api/v1/catalog/refresh`: для обычной
сессии нужен настроенный, подтверждённый HTTP источник из БД; оператор может
обновить local XML. Общий SQL интервал — 60 секунд для всех пользователей/replicas;
UI показывает остаток и блокирует кнопку, сервер возвращает 429/Retry-After.
Replay принятого Idempotency-Key не создаёт дубль и не продлевает интервал.
Ручной запуск не сдвигает scheduler. URL и credentials из тела запроса не принимаются.

Административный `/catalog/imports` с CatalogKey/операторской ролью и CLI импорт
оставлены без нового пользовательского cooldown для bootstrap и совместимости.
Настройка API 1С без подтверждённого контракта не разрешает публичное обновление.

## Ручная приёмка

1. Откройте `http://<сервер>:8087/`: интерфейс по концепту renders, без входа/регистрации.
   В справочнике видны реальные count, дата, fingerprint и карантин трёх кодов.
2. Укажите UUID извлечения, созданного **тем же API-ключом**, который задан серверу.
   Должны смениться этапы ожидания, загрузки и сопоставления. Итог сохраняет все
   строки и дубли, исходные Caption/Units/Quantity/Pages/UserComment1.
3. Откройте «Выбрать»: видны Top-K, код, единица, score, причины конфликтов. Найдите
   другую позицию по коду/артикулу, сохраните и перезагрузите страницу. Выбор остаётся.
4. Нажмите крестик у выбранной номенклатуры: появятся «Соответствие не выбрано»,
   «Не найдено / Подтверждено человеком». Исходная строка и Top-K остаются. Проверьте
   также вариант «нет подходящей позиции», фильтры, поиск, пагинацию и totals.
   В двух вкладках проверьте 409 при сохранении со старой revision.
5. С готовым результатом, в том числе со спорными строками, кнопка утверждения активна.
   Нажмите «Утвердить результат» без обхода каждой строки: текущие выборы и null
   подтверждаются вместе, без автоматического выбора новых кандидатов. Появляются
   финальный JSON и время утверждения; выбор
   заблокирован и после reload. Скачайте approved.json. Также проверьте
   source.json, предварительный result.json и утверждённый Excel по прежнему result.xlsx.
   До утверждения кнопка Excel недоступна, API отвечает 409 not_approved; после него
   лист «Лист_1» содержит A:S из шаблона Extracting и шесть столбцов T:Y.
   Оригинальная пятёрка неизменна, включая
   Quantity строкой и UserComment1. В legacy XML настоящий GUID 1С пуст;
   после HTTP JSON импорта ожидается настоящий `onec_guid`, внутренний UUID явно отдельный.
   При ручном поиске вне Top-K отсутствующая оценка остаётся пустой.
6. В приватном окне не должны быть видны задания первой сессии. Ключ upstream
   отсутствует в HTML и запросах браузера. Настройки и local XML закрыты без роли;
   публичное обновление доступно только подтверждённому HTTP источнику, с минутным
   лимитом. Проверьте роль оператора, получение кода, logout и сохранение обычного owner.
7. Во время обработки перезапустите **только worker этого проекта**, повторите доставку
   и убедитесь, что задача возобновляется без копий. Не перезапускайте общий RabbitMQ.
8. Через час после terminal состояние должно стать недоступным; ручной выбор не
   продлевает TTL. Каталог, XML и volumes при очистке заданий сохраняются.
9. Для приёмки качества сравните Top-K на реальных размеченных спецификациях:
   конфликтующие DN/PN/единицы не должны становиться автоматическим соответствием.

## Диагностика и откат

```bash
docker compose --env-file .env.example --env-file .env ps
docker compose --env-file .env.example --env-file .env logs --tail=100 api worker operator-gateway migrate
curl --fail http://127.0.0.1:8087/health/live
curl --fail http://127.0.0.1:8087/health/ready
curl --fail http://127.0.0.1:8087/api/openapi.json
```

`/health/live` — процесс; `/health/ready` проверяет реальные подключения и consumer.
Статус каталога показывает last_error отдельно от working snapshot. Повреждённый XML,
count mismatch или несовместимая embedding identity не подменяют каталог пустым.
Устраните источник ошибки и повторите импорт. При отказе DB commit alias автоматически
возвращается; при аварии между системами поиск всё равно использует concrete DB snapshot.
Не удаляйте PostgreSQL/Qdrant volumes для восстановления и не применяйте старые
миграции из examples/legacy к новой БД.

Старые версии сохраняются для ссылок заданий и отката. Worker раз в час удаляет
зарегистрированные snapshots старше часа, если это не active/previous и на них не
ссылается ни одно живое задание. Сборка версий использует тот же advisory lock.
Активный каталог, XML и embedding-кэш этим обслуживанием не удаляются.
Резервируйте PostgreSQL и Qdrant как данные этого проекта, независимо от shared stack.

## Сеть и доступ с другого компьютера

APP_BIND=0.0.0.0, APP_PORT=8087, APP_PUBLIC_BASE_URL=http://192.168.55.3:8087.
Обычные параметры — в .env.example/окружении команды; секреты — только в .env.
Web/API публикуют один порт; 8084 занят document-intake. Перед запуском:

```bash
ss -ltnp 'sport = :8087'
docker ps --format '{{.Names}} {{.Ports}}'
docker network inspect ai-shared
sudo ufw status verbose
sudo nft list ruleset
```

Firewall в ходе разработки не изменяется. Если политика требует разрешения,
оператор после проверки существующих правил может добавить LAN-правило UFW:
`sudo ufw allow from 192.168.55.0/24 to any port 8087 proto tcp`.
Docker published ports могут обходить UFW: проверить DOCKER-USER/nftables, маршрутизатор
и отсутствие доступа из недоверенных сетей. Не публиковать 5432/6333/5672 для этого
проекта, не менять чужие правила. Для интернета отдельно настроить HTTPS reverse
proxy, public URL, COOKIE_SECURE=true и политику доступа.

С Windows после успешного up.sh:

```powershell
Test-NetConnection 192.168.55.3 -Port 8087
Invoke-RestMethod http://192.168.55.3:8087/health/ready
Start-Process http://192.168.55.3:8087/
```

Секреты оператор читает локально в защищённой .env, не через команды, печатающие
credentials в общий журнал. Ключи onec/telegram передаются соответствующим
разработчикам защищённым каналом; upstream key берётся из конфигурации extracting.
Если пароль существующего RabbitMQ user не совпадает, bootstrap останавливается:
восстановить согласованное значение RABBITMQ_PASSWORD, не сбрасывать shared пароль.

## Главная и синхронизация V2/V3

Обновление использует прежний `bash scripts/up.sh`, порт 8087 и существующие volumes.
Перед обновлением дождаться текущего импорта; additive 0003 не трогает снимки и approvals.
Новый собственный volume catalog_staging нужен для HTTP загрузок; data остаётся read-only.
Bootstrap env-флаг применяется один раз; далее расписание хранится в PostgreSQL.
В V3 добавлен собственный loopback gateway, пользовательский минутный cooldown,
общее утверждение и очистка selection; новой DB миграции или секрета нет.
Не выполнять down -v, prune или downgrade ради rollback интерфейса.
[Настройки и доступ оператора](DASHBOARD_AND_SYNC.md),
[историческая проверка/deploy/rollback выпуска V2](RELEASE_V2.md). Для текущего
операторского входа используется описанный выше tunnel на 8088, не старый пример V2.

Для доверенного loopback-входа preflight требует Docker Engine 28+ (на тестовом
сервере проверен 29.8.1). В более старых версиях ограничение публикации localhost
имело сетевой обход, описанный в [Docker Docs](https://docs.docker.com/engine/network/port-publishing/).
Проверка не обновляет Docker и не меняет daemon/firewall. Сеть operator_access
отдельная, содержит только API и gateway; она не internal, поскольку Docker не
публикует host-порт для gateway, подключённого только к internal-сети.

Текущий выпуск: [V3 — результаты проверок, файлы и команды](RELEASE_V3.md).
